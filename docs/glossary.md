# Glossary

The canonical vocabulary for hashd. Other docs link here on first use of a term.
For the authoritative state model and lifecycle diagrams, see **[WF.md](../WF.md)**;
for the full product specification, see **PRD.md**.

## Entities

### Suggestion

A discovered planning candidate that can be claimed into a Story. `hashd plan` reads
the project's requirements (normally `REQS.md`) and produces suggestions in the
`suggestions` table. An operator inspects them (`hashd plan list`) and claims one to
create a Story. Suggestions have their own short lifecycle: `available -> claimed
-> done` (with `claimed -> available` revert). See **[WF.md > Suggestion
Lifecycle](../WF.md)**.

### Story

The unit of planned product work — a feature or bug with a problem statement and
**acceptance criteria**. A story is created from a Suggestion, from `hashd plan story`
/ `hashd plan bug`, or by cloning/editing an existing story. It flows `drafting ->
draft -> accepted -> implementing -> implemented` (with `editing`, `draft_failed`,
and `abandoned` branches). A story is the *source of truth* for what a change is
supposed to do; the requirement text it fulfills is frozen onto the story so it
reads standalone even after `REQS.md` is edited. See **[WF.md > Story
Lifecycle](../WF.md)**.

### Acceptance criteria (AC)

The bulleted, testable conditions a Story must satisfy to be considered done.
ACs are *input documentation* that grounds the implementer and reviewer — they
are not completion markers, and merge readiness is gated by FSM state and review
verdicts, not by checking off AC bullets. Operators reshape ACs with `hashd plan
{edit-ac, delete-ac, descope-ac, rescope-ac}`.

### Workstream

An implementation initiative bound to one git branch and one isolated git
worktree. Running an accepted Story creates a Workstream. The Workstream holds the
**plan** (the micro-commit list), drives the implement -> test -> review ->
human-gate loop for each micro-commit, and tracks all git, runner, PR, and
failure state. One Workstream = one branch + one worktree. See **[WF.md >
Workstream State Model](../WF.md)**.

### Micro-commit

The smallest planned unit of work inside a Workstream's plan — one focused change
that the implement/test/review loop runs to completion and commits as a single
git commit. Micro-commits are stored as Markdown headings in the plan with an
explicit done marker:

```markdown
### COMMIT-AUTH-001: Add token validator
- Description: ...
- Tests: go test ./...
Done: [ ]
```

Small, reviewable commits are a core operating principle: one micro-commit per
implementation cycle. Because every line in a micro-commit is agent-generated by
definition, the micro-commit is also the natural attribution boundary for lineage.

### Project

A registered product repository — or a multi-repo container — with hashd
configuration. Planning happens at the project level; execution happens per repo.
A project repo carries a role: `primary`, `active`, `reference`, or `ignore`.

### Project artifacts

The configured project documents hashd reads and updates as work moves through the
system. The two core artifacts are REQS.md and SPEC.md. Inspect them with
`hashd project reqs` / `hashd project spec`; make guarded manual edits with
`hashd project reqs edit` / `hashd project spec edit`.

### REQS.md

The project's requirements source. Discovery reads it to create Suggestions, and
planning annotates active story scope with WIP markers. Treat text between
`BEGIN WIP` and `END WIP` markers as story-owned: `hashd project reqs edit` rejects
changes inside those sections so manual edits cannot clobber active planning
state.

### SPEC.md

The project or repo specification hashd grows after successful work. Direct merges
update SPEC.md from the story and resulting diff, then commit it with REQS cleanup.
Use `hashd project spec` to inspect the configured artifact and `hashd project spec edit`
for guarded manual corrections.

### Clarification

A durable human question raised by an agent during planning or implementation
that blocks progress until answered. Clarifications are recorded in SQLite and
answered with `hashd answer`; answering can dispatch the next agent run. See
**[WF.md > Questions and Answers](../WF.md)**.

### Directive

Operator-authored standing guidance injected into agent prompts. Directives live
at global, project, or workstream scope and can be scoped to specific stages.
They are documentation, not runtime state.

## State model

A Workstream's runtime position is described by three orthogonal fields. The
canonical reference is **[WF.md > Workstream State Model](../WF.md)**; this is the
short version.

### stage

The macro FSM lifecycle position — *where* in the lifecycle a Workstream is:
`provisioning`, `active`, `implementing`, `awaiting_human_review`,
`ready_to_merge`, `merging`, `merge_conflicts`, `resolving`, `pr_open`,
`pr_approved`, `merged`, `closed`, and so on. Every change of stage goes through a
validated FSM transition. (In today's code this column is still named `status`;
`stage` is the canonical name per the migration outline in WF.md.)

### runtime_status

A *derived* field — computed on read from primitive Workstream fields, never
stored as a column — that says *what is happening* at the current stage right now.
Seven values: `running`, `blocked`, `changes_required`, `failed`, `idle`,
`orphaned`, `done`. Because it is derived, hard kills self-heal: a dead runner pid
flips the status to `orphaned` on the next read. The canonical compute function is
Go-server-side (`server/internal/fsm/runtime_status.go`) with a Python mirror
(`orchestrator/lib/workstream_status.py`); a cross-language contract test keeps
them in lockstep.

### runner_stage

The substage position inside a stage that has its own sub-FSM. For example,
`implementing` cycles through `preflight -> select -> clarification_check ->
concern_triage -> implement -> test -> review -> qa_gate -> commit`. Operator
displays render the trio as `<stage> / <runtime_status> (<runner_stage>)`.

## Process concepts

### Gate

A point in the lifecycle where work pauses for a verdict before it may proceed.
The governed loop has several: the **test gate** (configured tests must pass), the
**review gate** (the AI reviewer must approve, or request changes), the **human
review gate** (`awaiting_human_review`, where an operator approves/rejects/resets),
the **final-review gate** (a holistic branch review after all micro-commits land),
and the **merge gate** (merge-gate tests, conflict checks, and a secrets scan
before changes land). Whether a given gate auto-passes or stops for a human is
governed by the project's autonomy mode. See [how-hashd-works.md](how-hashd-works.md).

### Autonomy mode

The per-project setting that decides which gates stop for a human:
`supervised` (human approves every gate), `gatekeeper` (auto-continue commits when
review confidence clears a threshold, human approves merge — the default), and
`autonomous` (auto-continue commits and auto-merge when thresholds are met). All
three still block to a human on failures; the modes differ only in the merge-time
and per-commit gating.

### Dual-write event

The contract that every state change is written to two places: published to the **event bus**
for instant push to connected subscribers (TUI, Telegram, web), and logged to the
durable **SQLite events table** for catch-up by subscribers that were offline. the event bus
is ephemeral; SQLite is the durable source of truth. The events table is also the
spine of the audit trail. See [provenance.md](provenance.md).

### Attestation / lineage

**Lineage** is the chain that answers "why does this code exist?" — tracing a line
of code back through its commit, micro-commit, run, prompt, agent call,
workstream, story, requirement, reviews, and the human decisions that gated it.
`hashd lineage` walks the chain in either direction. An **attestation** is a
machine-readable export of that chain — `hashd lineage export` emits SLSA v1.0
provenance or an in-toto statement — and `hashd lineage verify` validates the
SHA-256 hash chain that links commit records. See [provenance.md](provenance.md)
and **[docs/LINEAGE.md](LINEAGE.md)**.

## Interfaces

### Dashboard

The home screen of the `hashd watch` TUI and hashd's navigation hub. It lists the
project's active Workstreams (selectable `1-9`) and Stories (selectable `a-i`),
and is the jumping-off point to the Plan screen (`p`), the autonomy-mode switch
(`m`), the command palette (`/`), and context-aware help (`?`). From the Dashboard
you drill into a Workstream Detail or Story Detail view and back. See
[watch.md](watch.md).

### Workstream Detail / Story Detail

The two drill-down views the Dashboard opens into. Workstream Detail is the
operator cockpit for a single in-flight Workstream — diff, log, review, timeline,
and the state-aware action keys (run, approve, reject, reset, replan, merge).
Story Detail is for shaping a Story before and during planning — approve, edit,
reshape acceptance criteria, and launch the Workstream. See
[watch.md](watch.md).
